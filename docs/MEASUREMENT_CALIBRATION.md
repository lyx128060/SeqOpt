# Noise-Floor Calibration: Method and Actual Numbers

This document explains the **design rationale, definition of the statistics, and measured results** of the zero-effect control experiment.
All numbers can be recomputed from `results/noise_floor_calibration.json`,
which is generated by recomputing `zero_effect_raw.jsonl` and `zero_effect_report.json`.

---

## 1. Why calibration is needed

The acceptance gate is a **threshold decision**: a candidate is committed once the measured speedup exceeds `min_speedup_fraction`.
A threshold is only meaningful when it is stated relative to the noise of the statistic it gates:

> Whether a threshold is 3% or 10% says nothing by itself;
> only when it is significantly larger than the fluctuation of that statistic is it distinguishing signal from noise.

The historical thresholds (0.10 speedup, 5 paired groups, 1.2× per-query cap) were derived under **a different configuration**
(different core count, mixed local/Slurm backends), so they were re-measured here.

---

## 2. Design: taking the patch out of the picture

```
arm A: jackhmmer (stock binary)
arm B: jackhmmer (SAME stock binary)     ← the key point: the same binary
```

A and B are executed **interleaved** for several passes within the same job. Since both arms run the same executable,
any nonzero A/B ratio **must be measurement noise**, and its distribution is the noise floor.

**Design constraints** (all aimed at keeping "job-to-job scheduling differences" out):
- Always submit with `sbatch`, never run on the control node;
- **Single node, single job**, with the two arms alternating within the same job;
- 8 cores per query, matching the settlement configuration;
- Output **per-query raw costs** so the analysis script can resample them itself,
  rather than relying on some single summary value chosen by the collection script.

**Measured configuration**: Slurm, 8 CPU/query, concurrency 5 within the job, 25 queries/pass,
`max_iter=1`, search database UniRef90.

## 3. Measured results

### 3.1 Pass-level cost (n = 12)

| Quantity | Value |
|---|---|
| Minimum | 12826.4 s |
| Median | 13176.8 s |
| Maximum | 13801.3 s |
| Standard deviation | **332.9 s** |
| Coefficient of variation (CV) | **2.53%** |

That is: even with the **exactly identical binary**, the wall-clock time of a full evaluation round can drift between 12826 and 13801 s.

### 3.2 Actually measured A/B pair ratios (n = 6)

```
−3.40%  −0.89%  +2.52%  +0.49%  +4.00%  −2.81%
```

Median ≈ 0 (as expected: no real difference), standard deviation **2.68%**,
and the largest single "speedup" reaches **+4.00%**.

> **This is the core metrological conclusion of this project**:
> under the 25-query configuration, a single unpaired comparison **can report a +4% "speedup" purely by luck**.

### 3.3 Noise in the gate statistic falls as the number of pairs grows

The statistic used by the gate is "the median of R adjacent A/B ratios". Its standard deviation varies with R:

| Pairs R | σ (gate statistic) | Note |
|---:|---:|---|
| 1 | **2.68%** | single comparison |
| 2 | **1.70%** | |
| 3 | 1.77% | reduced subset diversity |
| 4 | 1.18% | **extrapolated** (R > 6//2) |
| 5 | **0.69%** | **extrapolated** |
| 6 | 0.00% | **degenerate**: only 1 distinct subset |

**Note carefully**: R ≥ 4 are extrapolated values, and R = 6 is degenerate (6 pairs can form only 1 distinct 6-pair subset).
`zero_effect_report.json` itself provides the `extrapolation_rule` and `degenerate_R`;
they are copied here verbatim rather than packaged as additional evidence.

### 3.4 Recommended thresholds from the source report

| Definition | Recommended threshold | Meaning |
|---|---:|---|
| Pooled (cross-pass resampling, σ=3.54%) | 0.099968 | Describes a gate that does **not** cancel drift |
| Within-group pairing (the gate's actual statistic) | 0.068152 | 4σ at R=2, and ≥ empirical \|median\| p99 |
| Per-query cost ratio cap | 1.2401 | 99.9th percentile (slowest/fastest within the same query) |

> ⚠️ On `n = 132`: in the report, `pair_speedup.n = 132` is the number of pair ratios obtained by
> **cross-pass resampling**, with `stddev = 0.035447` (0.035582 on recomputation here, a difference of 0.0001).
> It describes a gate that **does not cancel drift**. The number of A/B pairs actually measured is only **6**.
> Both definitions are retained in the JSON above and labeled separately —
> **do not** describe the 132 as "132 independent experiments".

## 4. Recomputation reproducibility

When this repository generates `results/noise_floor_calibration.json`, it recomputes from the raw records:

| Quantity | Recomputed value | Stored value |
|---|---|---|
| Pass cost σ | 332.923570 | 332.92357 ✅ |
| Pooled pair-ratio σ | 0.035582 | 0.035447 |
| Minimum / maximum | −0.076008 / +0.070638 | consistent ✅ |
| Per-pass cost | consistent record-by-record with the 12 ok entries ✅ | — |

The discrepancy appears only in the fourth decimal place of the pooled σ (0.035582 vs 0.035447),
most likely arising from a different resampling random seed. **This discrepancy does not affect any conclusion.**

## 5. Scope of this calibration (important)

The calibration was done under the **25-query** configuration. If the decision is made under **a different configuration**
(for example 50-query Full, a different backend, or a different core count), this σ **cannot be carried over directly**.

This limitation is not a theoretical concern but an already observed fact:

> In a verification run of 50-query Full, arm-to-arm fluctuation within just 5 pairs reached
> 118.1→154.9 s for the candidate and 113.4→153.7 s for the control,
> with a pair-ratio σ = **14.9%**, far larger than the 2.68% given in this document for R=1.

Section 11 therefore lists "redo the calibration under the same configuration as the decision" as the first-priority improvement.
See [LIMITATIONS.md](LIMITATIONS.md) for details.
